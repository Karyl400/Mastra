# ADR-002 : Clean Architecture et Structure du Projet

## Statut
Adopté

## Contexte
Le projet nécessite une architecture modulaire, testable et maintenable qui isole les préoccupations métier des frameworks et de l'infrastructure.

## Décision
Nous adoptons la Clean Architecture avec les couches suivantes :

```
src/
  domain/entities/      # Entités métier pures (POJO)
  domain/ports/         # Interfaces de repository (dépendances inversées)
  application/use-cases/# Cas d'utilisation orchestrant la logique métier
  infrastructure/       # Implémentations concrètes (DB, notifications, etc.)
  agents/               # Agents Mastra
  tools/                # Outils Mastra (createTool)
  workflows/            # Workflows Mastra
  prompts/              # Templates de prompts
  shared/               # Types communs, validation, logger
  config/               # Configuration (variables d'environnement)
  mastra/               # Point d'entrée Mastra
```

Règles de dépendance :
- `domain/` ne dépend d'aucune autre couche
- `application/` dépend de `domain/`
- `infrastructure/` dépend de `domain/` et `application/`
- Les agents, outils, workflows dépendent de `domain/` et `application/`

## Conséquences
Positives :
- Testabilité : chaque couche peut être testée isolément
- Framework agnostic : le domaine ne dépend pas de Mastra
- Évolutivité : remplacer SQLite par Postgres ne touche que `infrastructure/`

Négatives :
- Plus de fichiers et d'indirection qu'une architecture monolithique
- Nécessite une discipline stricte pour maintenir les dépendances
